# TurboQuant

**Paper:** TurboQuant: Online Vector Quantization with Near-optimal Distortion Rate (Zandieh, Daliri, Hadian, Mirrokni, arXiv:2504.19874, April 2025; presented at ICLR 2026).

**Related work:** PolarQuant (random preconditioning plus polar and scalar quantization, AISTATS 2026); QJL, 1-bit Quantized Johnson-Lindenstrauss transform for KV Cache (arXiv:2406.03482).

**Authors' blog summary:** Google Research blog, March 24, 2026.

![Overview of the TurboQuant pipeline: rotate, quantize, then correct the residual](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image1.png)

## Why the KV Cache Needs Compression

![Growth of KV Cache memory with context length](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image2.png)

A decoder Transformer generates text one token at a time. At each step, attention over all past tokens would require recomputing their keys and values, so the model caches them. This cache is the KV Cache.

### KV Cache

![Attention recomputation without cache versus reuse with KV Cache](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image3.png)

Every time a new token is generated, attention computes interactions between the current query and the keys and values of historical tokens. To avoid repeated computation, the keys and values of past tokens are stored. When the context reaches hundreds of thousands or millions of tokens, this cache can exceed the size of the model weights and becomes the main memory bottleneck for serving.

### Memory Usage Example

![Example of KV Cache memory for long contexts](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image4.png)

Long-context inference is expensive largely because of this cache. As a rough example, a very long context on a large model can require on the order of a terabyte of GPU memory for the cache alone, which limits batch size and concurrency.

## Core Idea of TurboQuant

TurboQuant is an online, data-oblivious quantization method for the KV Cache. It keeps the full attention structure and compresses only how key and value vectors are stored. Compression happens in two stages:

```text
Stage 1, main quantization: random rotation followed by near-optimal
  scalar quantization (the PolarQuant construction).
Stage 2, residual correction: a 1-bit Quantized JL sketch (QJL) of the
  quantization residual, used to recover an unbiased estimate of
  attention inner products.
```

The first stage minimizes mean squared error. The second stage exists because a quantizer that is optimal for mean squared error still leaves bias in inner products, and attention depends on inner products. QJL does not reconstruct the original vector directly. It supplies a low-cost correction so the estimated query-key inner product stays close to unbiased.

:::info[Where the bit numbers come from]
Effective precisions such as 2.5-bit or 3.5-bit are averages. A small set of outlier channels is quantized at higher precision and the remaining channels at lower precision. For example, 32 channels at 3 bits and 96 channels at 2 bits averages to 2.5 bits per channel.
:::

## Random Rotation

Traditional scalar quantization struggles when a few coordinates are much larger than the rest. The quantization grid must stretch to cover the outliers, and small values fall into the same bin and become indistinguishable.

TurboQuant applies a random orthogonal rotation before quantization. An orthogonal transform preserves Euclidean norms and inner products when the same rotation is applied to both sides, so the geometry that attention relies on is unchanged. The rotation spreads the energy of outlier coordinates across many dimensions, so no single coordinate dominates.

After rotation in high dimensions, individual coordinates follow a concentrated distribution with a known analytic form, close to Gaussian. A scalar quantizer matched to that distribution (Lloyd-Max) then performs near-optimally without per-block scale and zero-point parameters. Avoiding those per-block parameters is where much of the memory saving comes from, since traditional block-wise methods must store them in full precision.

## Main Quantization Stage

![Grouping of rotated coordinates for quantization](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image8.png)

![Separation of quantization bins for the main stage](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image9.png)

The rotated vector is quantized coordinate by coordinate with the matched scalar codebook, typically at 3 to 4 bits. Dequantization maps each index back to its centroid and applies the inverse rotation to return to the original space. The result approximates the original key and value vectors well in mean squared error, but the remaining error still perturbs attention inner products enough to matter at very low bit widths.

![Dequantization path back to the original embedding space](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image10.png)

Because attention computes inner products between queries and keys in the original embedding space, the dequantized vectors must re-enter that space before attention runs. The main-stage reconstruction alone is not accurate enough at ultra-low widths, which motivates the residual stage below.

## QJL Residual Correction Stage

![QJL sketch of the quantization residual for inner-product correction](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image11.png)

The residual is the difference between the original vector and its main-stage reconstruction. QJL projects this residual with a random matrix and keeps only the sign of each projection, which costs about 1 bit per projection. At query time, the same projection applied to the query lets the system estimate the missing inner-product term. The estimate is unbiased by construction, so attention scores stay centered on their true values even though each individual sketch is coarse.

:::caution[Scope of the published quality claims]
The paper reports near-lossless LongBench scores at an effective 3.5 bits and small degradation at 2.5 bits, plus faster attention-logit computation (up to about 8x for 4-bit keys against a 32-bit baseline on H100). That speedup applies to attention logits, not to end-to-end inference, and independent reproductions have reported larger drops at 3 bits on reasoning and very long retrieval tasks. Treat 3-bit settings as workload-dependent.
:::

## Experimental Results

On LongBench, TurboQuant at an effective 3.5 bits scores close to the full 16-bit cache (around 50.1 in the reported average), while a comparable method such as KIVI needs around 5 bits to reach similar quality. A PolarQuant-only variant without the QJL stage drops noticeably, which indicates that the residual correction carries much of the gain at ultra-low widths.

| Setting | Effective bits | Reported behavior |
| :--- | :--- | :--- |
| Full cache | 16 | Reference quality |
| TurboQuant | 3.5 | Near reference on LongBench |
| TurboQuant | 2.5 | Small degradation on average |
| KIVI | 5 | Similar quality at higher width |
| PolarQuant only | Low | Visible drop without QJL |
