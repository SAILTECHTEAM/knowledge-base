# Lightning Philosophy

## What Is PyTorch Lightning

PyTorch Lightning is a lightweight wrapper around PyTorch that separates research code from engineering boilerplate. It provides a structured framework for building deep learning models without sacrificing flexibility.

Lightning is not a high-level API that hides PyTorch — it is a thin layer that automates the parts of training that are repetitive across projects while letting you control the critical research logic.

## The Core Philosophy

Lightning operates on a single principle: **separate research code from engineering code**.

### Research Code (Your Responsibility)

- Model architecture
- Loss function and metrics
- Training step logic (forward pass, loss computation)
- Validation/test step logic
- Optimizer configuration

### Engineering Code (Lightning Automates)

- Epoch and batch iteration
- Device placement (CPU, GPU, TPU)
- Mixed precision training (AMP)
- Gradient synchronization in distributed training
- Checkpointing and model saving
- Logging integration
- Early stopping and learning rate scheduling
- Debugging utilities (profiling, fast dev runs)

This separation means you write the same research code whether training on one GPU or 1000 GPUs.

## Why Lightning Exists

Despite PyTorch being incredibly flexible, research teams frequently face these challenges:

### Boilerplate Repetition

Every PyTorch project implements the same training loop:

```python
for epoch in range(num_epochs):
    for batch in dataloader:
        optimizer.zero_grad()
        output = model(batch)
        loss = criterion(output, target)
        loss.backward()
        optimizer.step()
```

This code is nearly identical across projects but takes up hundreds of lines. Lightning reduces this to:

```python
trainer.fit(model, datamodule=datamodule)
```

### Reproducibility Issues

Inconsistent training loops make it hard to reproduce results. Lightning standardizes every aspect of training — gradients are zeroed before the backward pass, optimizers step after backward, checkpointing happens at defined intervals. There is no ambiguity about what happens when.

### Scaling friction

Scaling from one GPU to multiple GPUs typically requires rewriting the training loop. Lightning makes this a single configuration change:

```python
# Single GPU
trainer = Trainer(accelerator="gpu", devices=1)

# Multi-GPU (just change this)
trainer = Trainer(accelerator="gpu", devices=4, strategy="ddp")
```

### Team Collaboration

When every project has a different training loop structure, code reviews focus on loop correctness instead of model logic. Lightning enforces a consistent structure that teams recognize immediately, making reviews faster and onboarding easier.

## When Lightning Feels "Rigid"

The most common criticism is that Lightning enforces structure — some developers feel constrained by hooks like `training_step` and `configure_optimizers`.

This rigidity is intentional. The constraints provide:

- **Consistency**: Every Lightning project follows the same structure.
- **Debugging**: When something breaks, you know exactly where to look.
- **Scaling**: The structured hooks make distributed training possible.
- **Maintainability**: Six months later, you understand your own code.

:::tip[Flexibility Within Structure]
Lightning provides multiple ways to accomplish the same task. Use [manual optimization](../02-core-components/01-lightning-module.mdx) when you need full control over the training loop, or subclass the Trainer for deep customization.
:::

## Distributed Training

One of Lightning's strongest benefits is native distributed training support. Without changing your model code, you can train on:

- **Single GPU**: Default behavior
- **Multi-GPU (DataParallel)**: `strategy="dp"` 
- **Multi-GPU (Distributed)**: `strategy="ddp"` or `"ddp_spawn"`
- **Multi-Node**: `num_nodes=N`
- **TPU**: `accelerator="tpu"`
- **DeepSpeed**: `strategy="deepspeed"`
- **FSDP**: `strategy="fsdp"`

The same model code runs on all these configurations — the only change is the Trainer flags.
## A Note on Lightning Fabric

If you want the device management and distributed scaling of Lightning without the rigid structure of `LightningModule` and `Trainer`, Lightning 2.0 introduced **Lightning Fabric**. 

Fabric is a fast and lightweight way to scale raw PyTorch. It provides a minimal `fabric` object that you inject into your existing raw PyTorch loops, giving you DeepSpeed, FSDP, and Mixed Precision support while letting you keep your exact custom training loop structure.

This tutorial focuses on the full `LightningModule` + `Trainer` experience, but keep Fabric in mind if you have an extremely custom loop that doesn't fit well into Lightning's hook system.
