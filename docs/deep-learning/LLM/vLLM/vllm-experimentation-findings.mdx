# vLLM Experimentation and Findings

This page documents the benchmark workflow, logs, results, and explanations from the one-GPU RTX 2080 Ti vLLM test. LLM inference theory is covered in [LLM Inference Principles](../llm-inference-principles), and serving setup is covered in [vLLM Setup](./vllm-setup).

## Test Scope

| Item | Value |
| :--- | :--- |
| GPU | NVIDIA GeForce RTX 2080 Ti |
| VRAM | About 11 GB |
| Serving framework | vLLM |
| Model | `QuantTrio/Qwen3.5-4B-AWQ` |
| Base model | `Qwen/Qwen3.5-4B` |
| Benchmark data | `vllm bench serve --dataset-name random` |
| Benchmark command family | `vllm bench serve` against the OpenAI-compatible chat endpoint |
| Canonical prompt count | `--num-prompts 200` |
| Seed | `--seed 0` |
| Output length | `--random-output-len 128` |
| vLLM dtype | `float16` |

:::caution[Scope]
These are infrastructure benchmark results from synthetic random prompts. They show serving behaviour for controlled input/output lengths, not product quality or production readiness.
:::

:::note[Why `float16` was used]
The tests used `--dtype float16` because the RTX 2080 Ti is a Turing-generation GPU with compute capability 7.5. This hardware path does not have the same `bfloat16` support assumptions as newer data-centre GPUs, so `float16` was the safer explicit dtype for this benchmark setup.
:::

## Metrics Used in Comparisons

| Metric | Meaning | How it was used in the comparison |
| :--- | :--- | :--- |
| Mean TTFT | Average time to first token. | Main signal for prefill and queueing cost. |
| P99 TTFT | Near-tail time to first token. | Used to expose queueing or scheduling spikes after moving to `n=200`. |
| Mean TPOT | Average time per output token after generation starts. | Main signal for per-request decode speed. |
| P99 TPOT | Near-tail time per output token. | Used to check whether decode latency became unstable under heavier active load. |
| Output tokens/s | Aggregate generated-token throughput over the benchmark wall time. | Compared against TTFT and TPOT to show the throughput/latency trade-off. |

One subtle point matters: output tokens/s is not decode-only speed. It is an aggregate benchmark throughput that includes time spent on prefill, queueing, and decode. That is why long prompts can reduce output tokens/s even when TPOT rises only modestly.

## Benchmark Workflow

Per-run variables made the result directories and benchmark files self-describing:

```bash
export MAX_MODEL_LEN="<server-context-window-tokens>"
export MAX_NUM_SEQS="<maximum-active-sequences>"
export MAX_NUM_BATCHED_TOKENS="<maximum-scheduled-tokens-per-step>"
export RANDOM_INPUT_LEN="<benchmark-input-tokens>"
export RANDOM_OUTPUT_LEN="<benchmark-output-tokens>"
export MAX_CONCURRENCY="<benchmark-client-concurrency>"
export GPU_MEMORY_UTILIZATION="<gpu-memory-fraction-for-vllm>"
export NUM_PROMPTS="<number-of-benchmark-requests>"
export SEED="<random-dataset-seed>"

export RUN_CONFIG_ID="<descriptive-run-config-id>"
export RUN_ID="<descriptive-run-config-id>-<timestamp>"
export RESULT_DIR="$WORKDIR/results/$RUN_ID"
export BENCH_FILE="$RESULT_DIR/bench-<descriptive-run-config-id>.txt"
mkdir -p "$RESULT_DIR"
```

The benchmark ran inside the vLLM container and targeted the OpenAI-compatible chat endpoint.

```bash
docker exec "$CONTAINER" vllm bench serve \
  --backend openai-chat \
  --endpoint /v1/chat/completions \
  --model "$MODEL" \
  --dataset-name random \
  --random-input-len "$RANDOM_INPUT_LEN" \
  --random-output-len "$RANDOM_OUTPUT_LEN" \
  --num-prompts "$NUM_PROMPTS" \
  --max-concurrency "$MAX_CONCURRENCY" \
  --seed "$SEED" \
  --ignore-eos \
  --save-result \
  --save-detailed \
  --result-dir "$RESULT_DIR" \
  --result-filename "bench-detailed.json" \
  | tee "$BENCH_FILE"
```

Synthetic random prompts were used because they avoid exposing sensitive data. They also make input and output lengths controllable, so `i1024/o128/c1` means the same basic workload shape across runs. The limitation is that random prompts do not represent natural language quality, user behaviour, or application-level answer usefulness.

:::note[Benchmark command notes]
`--ignore-eos` tells the benchmark to ignore early end-of-sequence tokens so outputs stay closer to the requested `--random-output-len`. This makes TPOT and output-throughput comparisons cleaner across runs. It is a benchmark-control option, not necessarily a production serving policy.

`tee "$BENCH_FILE"` prints the benchmark output to the terminal and writes the same output to the benchmark text file. This keeps the interactive run readable while preserving a copy for later reporting.
:::

## Artefact Capture

Capture evidence after each run:

```bash
docker image inspect "$IMAGE" \
  --format '{{index .RepoDigests 0}}' \
  > "$RESULT_DIR/image-digest.txt"
nvidia-smi -q > "$RESULT_DIR/nvidia-smi-final.txt"
docker logs "$CONTAINER" > "$RESULT_DIR/server.log" 2>&1
docker inspect "$CONTAINER" > "$RESULT_DIR/container-config.json"
```

`image-digest.txt` records the exact Docker image identity used for the run. This matters because tags such as `latest` can move between benchmark sessions.
`2>&1` ensures that both normal logs and error messages are saved into the exact same file. Without it, any application crashes or error messages will bypass your log file entirely and print to the screen instead.

`grep` can be used to pull relevant lines out of long logs. For example:

```bash
grep -iE "kv cache|maximum concurrency|memory|gpu|oom|error" "$RESULT_DIR/server.log"
```

Explanation:

- `grep` searches text files.
- `-i` makes the search case-insensitive.
- `-E` enables extended regular expressions.
- The `|` characters mean "or", so this example finds lines containing any of those keywords.

## Repeat Workflow

Use this loop for benchmark experiments:

```text
Set the current server-side limits.
Start the vLLM container.
Capture startup evidence and metrics-before.
Run the benchmark while sampling metrics.
Capture benchmark output, server logs, container config, GPU state, and image digest.
Stop and remove the container.
Change server-side limits if needed.
Start a fresh container and benchmark again.
```

To stop and remove the container after capturing artefacts:

```bash
docker stop "$CONTAINER"
docker rm "$CONTAINER"
```

This matters because `--max-model-len`, `--max-num-seqs`, `--max-num-batched-tokens`, and `--gpu-memory-utilization` are server startup choices. Changing those values requires a fresh vLLM server process. Benchmark-only values such as `--random-input-len`, `--random-output-len`, and `--max-concurrency` can change between benchmark commands only if the already-running server has enough capacity for the new shape.

## Theoretical Observations

| Serving component | Theoretical pressure | What to expect in metrics |
| :--- | :--- | :--- |
| Prefill | The attention-score component scales as $O(N^2)$ with prompt length $N$, while other per-token work is closer to $O(N)$. | TTFT should rise strongly with input length. The measured ratio can still be below the pure $N^2$ ratio because TTFT is the sum of several costs. |
| Decode attention | Each new token attends over the existing cached context, so attention work per generated token scales as $O(N)$ with current context length. | TPOT should increase much more gently than TTFT as context grows. |

## Code and Logs

The experiment used three canonical ladders plus one diagnostic:

| Experiment | What changed | Why it was tested |
| :--- | :--- | :--- |
| Input length | `i128`, `i512`, `i1024`, `i1800`. | Measures prefill growth under a 2048 context limit. |
| Context limit | 4096, 8192, 16384 max context. | Limit test for progressively larger serving shapes on one GPU. |
| Concurrency | Benchmark concurrency 1, 2, 4, 8. | Measures batching and queueing. |

### Input-Length Ladder

All runs below used `--max-model-len 2048`, `--max-num-seqs 1`, `--max-num-batched-tokens 2048`, `--gpu-memory-utilization 0.82`, `--num-prompts 200`, and `--seed 0`.

| Input | Output | Output tok/s | Mean TTFT | P99 TTFT | Mean TPOT | P99 TPOT |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 128 | 128 | 76.89 | 104.68 ms | 104.65 ms | 12.28 ms | 12.52 ms |
| 512 | 128 | 70.80 | 229.99 ms | 263.46 ms | 12.42 ms | 13.15 ms |
| 1024 | 128 | 61.93 | 444.17 ms | 456.24 ms | 12.77 ms | 12.93 ms |
| 1800 | 128 | 52.49 | 792.38 ms | 822.95 ms | 12.96 ms | 13.17 ms |

Observed scaling:

| Move | Input ratio | Pure $O(N^2)$ attention ratio | Mean TTFT ratio | Mean TPOT ratio |
| :--- | ---: | ---: | ---: | ---: |
| `128 -> 512` | 4.00x | 16.00x | 2.20x | 1.01x |
| `512 -> 1024` | 2.00x | 4.00x | 1.93x | 1.03x |
| `1024 -> 1800` | 1.76x | 3.09x | 1.78x | 1.01x |
| `128 -> 1800` | 14.06x | 197.75x | 7.57x | 1.06x |

The direction matches the expected prefill cost pattern: longer prompts mostly hurt TTFT because prefill has to process the whole prompt and write the KV cache before the first output token can appear. The exact curve is not quadratic in this range. For example, self-attention is only one part of a transformer layer; the model also performs per-token transformations before and after attention, and those parts scale more like $O(N)$ than $O(N^2)$. This is one possible reason the measured TTFT grew strongly but stayed below the pure quadratic attention ratio.

### Context-Limit Ladder

The context-limit ladder evaluates the operational limits of long-context deployment rather than isolated input scaling. The result should therefore be read as an operating-envelope test: how costly does the serving configuration become as vLLM is asked to support larger context windows on one GPU?

The 16384 context shape failed at `--gpu-memory-utilization 0.82` during engine startup. The error occurred while vLLM was initialising KV-cache capacity. To serve one full-length 16384-token request, vLLM estimated that 0.56 GiB of KV-cache memory was required, but only 0.23 GiB remained available after model loading, profiling, CUDA graph memory, and other runtime reservations. Under that memory budget, vLLM estimated the maximum supported model length as 5808 tokens. Raising `gpu-memory-utilization` to `0.90` gave vLLM a larger reservation budget and allowed the 16384 run to start, at the cost of reduced free VRAM headroom. The comparison table below reports the successful `gpu-memory-utilization 0.90` runs; all used benchmark concurrency 1 and 200 prompts.

| Max context | Input | Output | Output tok/s | Mean TTFT | P99 TTFT | Mean TPOT | P99 TPOT | VLLM memory |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4096 | 2048 | 128 | 48.26 | 968.22 ms | 984.73 ms | 13.26 ms | 13.49 ms | 8626 MiB |
| 8192 | 4096 | 128 | 30.96 | 2341.79 ms | 2401.46 ms | 14.11 ms | 14.39 ms | 9136 MiB |
| 16384 | 8192 | 128 | 15.21 | 6402.78 ms | 6626.26 ms | 15.84 ms | 16.48 ms | 9876 MiB |

The observed effect was not merely slower performance; it showed that the largest context shape was close to the practical limit of this GPU. As the context-serving shape grew, mean TTFT increased from 968.22 ms at 4096 context to 6402.78 ms at 16384 context, while output throughput fell from 48.26 to only 15.21 output tokens/s. That throughput is very low for an interactive serving target, especially because the run also required `gpu-memory-utilization 0.90`, leaving little VRAM headroom. Mean TPOT increased much more gently, from 13.26 ms to 15.84 ms, because decode reuses the KV cache created during prefill instead of recomputing the full prompt for every generated token. The practical conclusion is that 16384 context was a ceiling probe, not a sensible operating point for this RTX 2080 Ti setup.

The VLLM memory column should be interpreted as resident process memory, not live KV-cache usage. Increasing `--max-model-len` requires vLLM to plan for a larger possible KV-cache envelope, but the reported MiB values also include model weights, CUDA/runtime workspace, profiling allocations, and memory-pool behaviour.

### Concurrency Ladder

The concurrency ladder used the same workload shape, `i1024/o128`, while increasing benchmark concurrency from 1 to 8. The server was started with `--max-num-seqs 8`, `--max-num-batched-tokens 8192`, `--gpu-memory-utilization 0.82`, and `--num-prompts 200`, so the comparison focuses on batching, queueing, and KV-cache pressure.

| Benchmark concurrency | Output tok/s | Mean TTFT | P99 TTFT | Mean TPOT | P99 TPOT | Max running | Max waiting |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 62.67 | 431.37 ms | 447.43 ms | 12.68 ms | 12.84 ms | 1 | 0 |
| 2 | 97.91 | 638.89 ms | 867.79 ms | 15.55 ms | 17.47 ms | 2 | 0 |
| 4 | 141.96 | 1326.18 ms | 1693.87 ms | 17.95 ms | 25.76 ms | 4 | 0 |
| 8 | 140.41 | 4943.71 ms | 9813.48 ms | 17.92 ms | 25.49 ms | 4 | 4 |

Varying concurrency means the benchmark sends multiple requests to the server at the same time. vLLM can then batch work from different requests together so the GPU has more work to process in each scheduling step. This is why aggregate output tokens/s rises even when each individual request becomes slower: the server is producing tokens for more requests in parallel.

The trade-off is that each request now shares GPU compute, memory bandwidth, scheduler time, and KV-cache capacity with other active requests. TTFT increases because requests may wait behind other prompts before their own prefill finishes. TPOT also increases because each decode step is no longer serving just one sequence; the server is moving through a larger active batch and reading KV-cache blocks for multiple requests.

The P99 TPOT values show that decode latency also became less stable. At `c1`, P99 TPOT was close to mean TPOT, 12.84 ms versus 12.68 ms. At `c4`, P99 TPOT rose to 25.76 ms while mean TPOT was 17.95 ms. This means most tokens were generated at the average pace, but some decode steps were much slower. For example, this can happen when scheduler steps have uneven work, when active requests are at different stages of prefill/decode, or when KV-cache memory traffic becomes more bursty under batching.

The theoretical KV-cache memory requirement grows roughly linearly with active sequences. If the server can keep more requests running, batching can improve GPU utilisation and aggregate output tokens/s. But once the GPU is saturated, or the KV-cache pool is exhausted, more client concurrency mostly becomes queueing.

The observed pattern matches that expectation:

| Move | Output tok/s change | Mean TTFT change | Scheduler signal | Interpretation |
| :--- | :--- | :--- | :--- | :--- |
| `c1 -> c2` | 62.67 to 97.91 | 431.37 ms to 638.89 ms | 2 running, 0 waiting | Better GPU utilisation with moderate latency cost. |
| `c2 -> c4` | 97.91 to 141.96 | 638.89 ms to 1326.18 ms | 4 running, 0 waiting | Best tested throughput at `gpuutil0.82`, but TTFT roughly doubled. |
| `c4 -> c8` | 141.96 to 140.41 | 1326.18 ms to 4943.71 ms | 4 running, 4 waiting, 100% KV usage | Throughput saturated; extra requests queued instead of improving useful work. |

This also explains why external memory snapshots can be misleading. vLLM's PagedAttention allocates KV-cache blocks from a memory pool planned at startup. `nvidia-smi` therefore mostly reports resident memory already reserved by vLLM plus transient runtime memory, not the exact live KV-cache consumption for each concurrency level. vLLM's internal metrics showed the real pressure: `c8` hit 100% GPU KV-cache usage and had four waiting requests.

### C8 GPU-Memory Diagnostic

Only `--gpu-memory-utilization` changed in this diagnostic:

| GPU memory setting | Output tok/s | Mean TTFT | P99 TTFT | Mean TPOT | P99 TPOT | KV cache size | Max full-context concurrency | Max running | Max waiting | Peak KV usage | VLLM memory |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | :--- | ---: | ---: | :--- | ---: |
| 0.82 | 140.41 | 4943.71 ms | 9813.48 ms | 17.92 ms | 25.49 ms | 7,314 tokens | 3.57x | 4 | 4 | 100% | 8196 MiB |
| 0.90 | 180.69 | 2800.85 ms | 7940.99 ms | 22.56 ms | 40.78 ms | 21,357 tokens | 10.43x | 8 | 0 | 66.7% | 9820 MiB |

This isolates the cause of the `c8/gpuutil0.82` queueing result. At `0.82`, vLLM had only 7314 KV-cache tokens available and reported maximum full-context concurrency of 3.57x for 2048-token requests. The benchmark wanted eight concurrent requests, so the scheduler could only run four at a time and left four waiting. At `0.90`, vLLM planned 21,357 KV-cache tokens, could run all eight requests, and throughput rose to 180.69 output tok/s.

The diagnostic also shows the cost of raising the memory setting. TTFT improved compared with the constrained `c8/0.82` run because fewer requests were waiting, but TPOT worsened from 17.92 ms to 22.56 ms and P99 TPOT worsened sharply. The server was doing more active decode work at once, which improved aggregate throughput but made per-request decode less stable. GPU resident memory also rose to 9820 MiB, leaving little headroom on the 11 GB GPU.
