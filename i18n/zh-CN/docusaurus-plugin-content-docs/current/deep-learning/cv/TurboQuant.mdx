# TurboQuant

**论文：** TurboQuant: Online Vector Quantization with Near-optimal Distortion Rate (Zandieh, Daliri, Hadian, Mirrokni, arXiv:2504.19874, 2025 年 4 月；在 ICLR 2026 发表）。

**相关工作：** PolarQuant（随机预处理加极坐标和标量量化，AISTATS 2026）；QJL，面向 KV Cache 的 1 比特量化 Johnson-Lindenstrauss 变换（arXiv:2406.03482）。

**作者博客总结：** Google Research 博客，2026 年 3 月 24 日。

## 为什么 KV Cache 需要压缩

![KV Cache 内存随上下文长度的增长](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image2.png)

解码器 Transformer 一次生成一个 token。每一步对全部过去 token 的注意力都要用到它们的键和值，重算一遍代价很高，所以模型把它们缓存下来，这就是 KV Cache。

### KV Cache

![不用缓存的重算注意力，与使用 KV Cache 的复用之对比](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image3.png)

每生成一个新 token，注意力都要计算当前查询与历史 token 的键和值的交互。为了避免重复计算，过去 token 的键和值被存下来。当上下文达到几十万甚至上百万 token 时，这个缓存可能超过模型权重本身，成为 serving 时主要的内存瓶颈。

### 内存占用举例

![长上下文下 KV Cache 内存的例子](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image4.png)

长上下文推理之所以贵，很大程度上是因为这个缓存。粗略地说，大模型上的很长上下文只算缓存就可能需要 TB 量级的 GPU 内存，批量大小和并发数都受它限制。

## TurboQuant 的核心思想

TurboQuant 是一种在线的、与数据无关的 KV Cache 量化方法。它保留完整的注意力结构，只压缩键向量和值向量的存法。压缩分两个阶段：

```text
第一阶段，主量化：随机旋转加上接近最优的
  标量量化（即 PolarQuant 的做法）。
第二阶段，残差修正：对量化残差做 1 比特量化 JL
  素描（QJL），用来恢复注意力内积的无偏估计。
```

第一阶段最小化均方误差。第二阶段之所以必要，是因为均方误差最优的量化器在内积上仍有偏差，而注意力依赖的正是内积。QJL 并不直接重建原向量，它用很低的代价修正估计，使查询和键的内积估计保持接近无偏。

:::info[比特数从哪里来]
2.5 比特、3.5 比特这类数字是平均值。少数离群通道用较高精度量化，其余通道用较低精度量化。例如 32 个通道用 3 比特、96 个通道用 2 比特，平均就是每通道 2.5 比特。
:::

## 随机旋转

传统标量量化最怕少数坐标远大于其余坐标。量化格子为了装下离群值被拉得很大，小数值落进同一个格子就分不开了。

TurboQuant 在量化之前先做一次随机正交旋转。对两边施加同一个旋转时，欧氏范数和内积都不变，注意力依赖的几何关系也就不变。旋转把离群坐标的能量分散到很多维度，不再有单个坐标一家独大。

在高维旋转之后，单个坐标服从一个集中且解析形式已知的分布，接近高斯分布。对这个分布配套的标量量化器（Lloyd-Max）接近最优，而且不需要每个数据块各自的缩放和零点参数。省掉这些全精度存放的块参数，是内存节省的主要来源之一，而传统按块量化必须存放它们。

## 主量化阶段

![旋转后坐标的分组量化](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image8.png)

![主量化阶段的量化区间划分](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image9.png)

旋转后的向量逐个坐标用配套的标量码本量化，一般在 3 到 4 比特。解量化把每个编号映射回对应的中心点，再做逆旋转回到原空间。得到的向量在均方误差下已经接近原始的键和值，但在很低的位宽下，剩下的误差仍然足以扰动注意力内积，这就是下面残差阶段的由来。

![解量化回到原嵌入空间的路径](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image10.png)

注意力在原嵌入空间里计算查询和键的内积，解量化后的向量必须先回到这个空间才能参与注意力计算。只靠主阶段的重建，在超低位宽下精度不够，所以需要残差阶段补上。

## QJL 残差修正阶段

![对量化残差做 QJL 素描以修正内积](https://raw.githubusercontent.com/SAILTECHTEAM/knowledge-base/main/static/img/cv_img/TurboQuantimg/image11.png)

残差是原向量与主阶段重建之差。QJL 用一个随机矩阵投影残差，只保留每个投影的符号，每个投影约花费 1 比特。查询到来时，对查询做同样的投影，就可以估计缺掉的内积项。这个估计按构造是无偏的，所以尽管每次素描都很粗，注意力分数仍然围绕真值波动。

:::caution[已发表质量结论的适用范围]
论文报道在平均 3.5 比特下 LongBench 分数接近无损，在 2.5 比特下平均只有小幅下降，注意力 logit 计算最快约 8 倍（H100 上 4 比特键相对 32 比特基线）。这个加速针对的是注意力 logit，不是端到端推理。独立复现发现在 3 比特下，推理和很长检索任务上的下降更大。3 比特的设置应当按任务看待。
:::

## 实验结果

在 LongBench 上，平均 3.5 比特的 TurboQuant 分数接近全量 16 比特缓存（报道的平均分约 50.1），而 KIVI 之类的方法要用约 5 比特才达到类似质量。不带 QJL 的 PolarQuant 变体下降明显，说明在超低位宽下增益主要来自残差修正。

| 设置 | 有效比特 | 报道的表现 |
| :--- | :--- | :--- |
| 全量缓存 | 16 | 基准质量 |
| TurboQuant | 3.5 | 在 LongBench 上接近基准 |
| TurboQuant | 2.5 | 平均小幅下降 |
| KIVI | 5 | 用更高位宽达到类似质量 |
| 只有 PolarQuant | 低 | 不带 QJL 时下降明显 |
